지난 편의 `boards` 와 마찬가지로 배열의 빈 줄이 설명 단위입니다.

### ① 소속 — `board_id`, `user_id`, `category`

`board_id` 는 이 강좌 전체에서 가장 자주 쓰이는 컬럼입니다. 1편에서 "게시판마다 테이블을 만들지 않는다"고 정한 순간부터, 글이 어느 게시판 것인지는 **이 컬럼 하나로만** 구분됩니다.

타입이 `boards.id` 와 정확히 같아야 합니다. `boards.id` 가 `INT UNSIGNED` 였으니 여기도 `INT UNSIGNED` 입니다. 한쪽만 `BIGINT` 로 두면 외래 키를 걸 때 거절당합니다. `user_id` 가 `BIGINT UNSIGNED` 인 것도 같은 이유입니다 — `users.id` 가 그렇기 때문입니다.

`user_id` 만 `NULL` 을 허용합니다. 두 가지를 뜻합니다.

| `user_id` | 뜻 |
|---|---|
| 값 있음 | 회원이 쓴 글 |
| `NULL` | 비회원이 썼거나, 쓴 사람이 탈퇴했거나 |

3편 8절에서 정한 대로입니다. 그리고 이 `NULL` 허용이 없으면 뒤에서 걸 `ON DELETE SET NULL` 자체가 불가능합니다. 넣을 값이 없으니까요.

`category` 는 `boards.categories` JSON 배열 안의 값 하나를 문자열로 그냥 들고 있습니다. FK 가 아닙니다 — 3편 4절 ②에서 이야기한 그 선택입니다.

### ② 본문 — `title`, `content`, `content_html`

`content` 와 `content_html` 이 나뉜 게 눈에 걸릴 수 있습니다. 같은 글을 두 번 저장하는 셈이니까요.

`content` 는 **사용자가 입력한 원본**입니다. `content_html` 은 그걸 화면에 뿌릴 수 있게 가공한 결과, 즉 **캐시**입니다. 줄바꿈을 `<br>` 로 바꾸고, 링크를 자동으로 걸고, 25편에서 에디터가 붙으면 위험한 태그를 걷어낸 결과가 여기 들어갑니다.

원본을 남겨두는 이유는 수정 화면 때문입니다. 가공된 HTML 을 다시 입력창에 넣으면 사용자가 쓰지 않은 태그를 사용자가 편집하게 됩니다. 몇 번 왕복하면 글이 망가집니다.

`content_html` 이 `NULL` 을 허용하는 건 아직 가공하지 않은 상태가 있기 때문입니다. 11편에서 글쓰기를 만들 때 이 컬럼을 채웁니다.

타입은 둘 다 `MEDIUMTEXT` 입니다. `TEXT` 로도 될 것 같은데, 한글에서는 생각보다 빨리 벽에 닿습니다.

| 타입 | 최대 바이트 | 한글로 환산(글자당 3바이트) |
|---|---|---|
| `TEXT` | 65,535 | 약 21,800자 |
| `MEDIUMTEXT` | 16,777,215 | 약 559만 자 |

`utf8mb4` 에서 한글 한 글자는 3바이트입니다. `TEXT` 컬럼에 한글 3만 자를 넣어 봤습니다.

```sql
INSERT INTO comments (post_id, content, created_at, updated_at)
VALUES (1, REPEAT('가', 30000), NOW(), NOW());
```

```
ERROR 1406 (22001): Data too long for column 'content' at row 1
```

같은 시도를 `MEDIUMTEXT` 인 `posts.content` 에 하면 통과합니다. 한글 30만 자를 넣고 다시 읽어 봤습니다.

```
id  title   chars    bytes
3   긴 글   300000   900000
```

한글 3만 자면 원고지 150매쯤입니다. 게시판 글로는 과한 길이지만, **긴 공지나 약관을 붙여넣는 순간 넘어갑니다.** 그리고 이 에러는 사용자가 글쓰기 버튼을 누른 뒤에야 납니다. 저장 실패로 글이 통째로 날아가는 자리라 넉넉하게 잡았습니다.

`comments.content` 는 `TEXT` 그대로 뒀습니다. 댓글에 2만 자를 쓰는 사람은 막는 편이 낫다고 봤습니다.

### ③ 플래그 둘 — `is_notice`, `is_secret`

`is_notice` 는 공지 상단 고정입니다. 목록 정렬이 `ORDER BY is_notice DESC, id DESC` 라, 이 컬럼이 1인 글은 항상 맨 위에 붙습니다(27편).

`is_secret` 은 비밀글입니다. `boards.use_secret` 이 켜진 게시판에서만 쓰입니다 — 게시판 설정이 기능을 열고, 글마다의 값이 실제 적용을 정합니다. 이 두 층 구조는 앞으로 계속 나옵니다.

### ④ 비회원 — `guest_name`, `guest_password`

회원 기능은 13편에 나옵니다. 그런데 게시판은 7편부터 동작해야 합니다. 그 사이 여섯 편 동안 글을 쓰는 주체가 비회원입니다.

`guest_password` 는 이름과 달리 **비밀번호를 담지 않습니다.** `password_hash()` 를 통과한 해시가 들어갑니다. 비회원이 자기 글을 수정하거나 지울 때 이걸로 확인합니다. 길이 255의 근거는 4편 2절에서 `users.password_hash` 를 이야기하며 다룬 것과 같습니다.

비회원 기능을 쓰지 않는 서비스라면 두 컬럼은 계속 `NULL` 입니다. 비어 있는 `VARCHAR` 는 공간을 거의 쓰지 않으므로 남겨둬도 손해가 없습니다.

### ⑤ 카운터 넷 — `unsigned` 의 함정

`view_count`, `comment_count`, `like_count`, `file_count`. 3편 5절에서 "카운터는 캐시다"라고 정리한 그 넷입니다.

전부 `INT UNSIGNED` 입니다. 음수가 될 수 없는 값이니 당연해 보이는데, 여기 함정이 하나 있습니다. 댓글을 지우면서 카운터를 줄이는 코드를 생각해 보겠습니다.

```sql
UPDATE posts SET comment_count = comment_count - 1 WHERE id = 1;
```

`comment_count` 가 이미 0인 글에 이 쿼리가 날아가면 이렇게 됩니다.

```
ERROR 1690 (22003): BIGINT UNSIGNED value is out of range in '(`ci4board`.`posts`.`comment_count` - 1)'
```

`UNSIGNED` 컬럼은 -1 을 만들 수 없어서 계산 자체가 실패합니다. 그리고 카운터는 캐시라 **언젠가 실제 댓글 수보다 앞서 나갑니다.** 0인데 한 번 더 빼려 드는 상황이 반드시 옵니다.

방어는 뺄셈 쪽에서 합니다.

```sql
UPDATE posts SET comment_count = GREATEST(comment_count, 1) - 1 WHERE id = 1;
```

0 이면 0 그대로 두고, 1 이상이면 하나 줄입니다. 22편에서 댓글 카운터를 붙일 때 이 모양을 씁니다.

> 에러 메시지가 `BIGINT UNSIGNED` 라고 말하는 게 이상해 보일 수 있습니다. 컬럼은 `INT` 인데요. MySQL 이 정수 연산을 내부적으로 더 큰 타입으로 올려서 계산하기 때문입니다. 컬럼 타입을 `BIGINT` 로 바꿔도 이 에러는 그대로 납니다.

### ⑥ 흔적 — `status`, `ip`

`status` 는 `published` / `hidden` 입니다. 소프트 딜리트(`deleted_at`)와 다릅니다.

| | 누가 | 뜻 |
|---|---|---|
| `status = 'hidden'` | 관리자 | 지운 건 아니고 안 보이게 했다 |
| `deleted_at IS NOT NULL` | 작성자 또는 관리자 | 지웠다. 되살릴 수 있다 |

신고가 들어온 글을 판단 전까지 내려두는 자리가 `hidden` 입니다(33편).

`ip` 가 `VARBINARY(16)` 입니다. 문자열로 두는 게 흔한데 이쪽을 골랐습니다. PHP 의 `inet_pton()` 이 IP 주소를 바이트로 바꿔 주는데, 결과 길이가 이렇습니다.

```php
foreach (['127.0.0.1', '203.0.113.9', '2001:db8::1'] as $ip) {
    $bin = inet_pton($ip);
    printf("%-14s %2d바이트  %s\n", $ip, strlen($bin), bin2hex($bin));
}
```

```
127.0.0.1       4바이트  7f000001
203.0.113.9     4바이트  cb007109
2001:db8::1    16바이트  20010db8000000000000000000000001
```

IPv4 는 4바이트, IPv6 는 16바이트입니다. `VARBINARY(16)` 하나로 둘 다 담깁니다. 문자열로 두면 IPv6 를 담기 위해 `VARCHAR(45)` 가 필요하고, 같은 주소를 표기만 다르게 적은 문자열(`2001:db8::1` 과 `2001:0db8:0000:...:0001`)이 서로 다른 값으로 저장됩니다.

DB 에서도 같은 변환을 함수로 할 수 있습니다.

```sql
INSERT INTO posts (board_id, title, content, ip, created_at, updated_at)
VALUES (1, 'IP 시험', '본문', INET6_ATON('203.0.113.9'), NOW(), NOW());

SELECT id, HEX(ip) AS raw, LENGTH(ip) AS bytes, INET6_NTOA(ip) AS readable FROM posts;
```

```
id  raw                               bytes  readable
1   CB007109                          4      203.0.113.9
2   20010DB8000000000000000000000001  16     2001:db8::1
```

대신 대가가 있습니다. **눈으로 읽히지 않습니다.** `SELECT ip FROM posts` 를 하면 깨진 글자가 나오고, IP 로 검색하려면 조건 쪽에도 `inet_pton()` 을 통과시킨 값을 넣어야 합니다. 이 컬럼은 화면에 거의 안 나오고 중복 조회 방지(10편)와 신고 처리(33편)에서만 쓰이므로 감수할 만하다고 봤습니다.

### ⑦ 시각 셋 — `created_at`, `updated_at`, `deleted_at`

앞의 둘은 4편에서 본 그대로입니다. 새로 붙은 건 `deleted_at` 입니다.

이 컬럼 하나가 12편의 주제 전체입니다. 값이 `NULL` 이면 살아 있는 글, 시각이 찍혀 있으면 지워진 글입니다. **DB 는 이 약속을 모릅니다.** 8절에서 그 이야기를 합니다.

## 2. 외래 키 — 선을 긋는다

`posts` 마이그레이션의 마지막 두 줄입니다.

```php
$this->forge->addForeignKey('board_id', 'boards', 'id', '', 'CASCADE', 'fk_posts_board');
$this->forge->addForeignKey('user_id', 'users', 'id', '', 'SET NULL', 'fk_posts_user');
```

네 번째 인자의 빈 문자열이 뭔지 알아야 나머지가 읽힙니다. 시그니처는 이렇습니다.

```php
addForeignKey(
    $fieldName,          // 이 테이블의 컬럼
    string $tableName,   // 가리킬 테이블
    $tableField,         // 가리킬 컬럼
    string $onUpdate,    // ← 갱신 규칙이 먼저
    string $onDelete,    // ← 삭제 규칙이 나중
    string $fkName = '',
)
```

**`onUpdate` 가 `onDelete` 보다 앞입니다.** 자주 쓰는 건 뒤쪽인데 순서는 앞이라, 둘을 바꿔 넣기 쉽습니다. 그래서 빈 문자열이 하나 끼어 있는 겁니다 — "갱신 규칙은 지정하지 않는다"는 뜻입니다. 지정하지 않으면 `ON UPDATE` 절 자체가 SQL 에 나가지 않고, 표준의 기본값인 `NO ACTION` — MySQL 에서는 `RESTRICT` 와 같습니다 — 으로 동작합니다. 부모 키가 바뀌려 하면 거절한다는 뜻입니다. `boards.id` 는 auto_increment 라 바뀔 일이 없어서 이대로 뒀습니다.

여기서 조심할 게 하나 더 있습니다. CodeIgniter 는 이 자리에 **허용된 값만 통과시키고, 나머지는 조용히 버립니다.**

```php
// system/Database/Forge.php
protected $fkAllowActions = ['CASCADE', 'SET NULL', 'NO ACTION', 'RESTRICT', 'SET DEFAULT'];
```

`'CASCASE'` 처럼 오타를 내면 어떻게 되는지 직접 만들어 봤습니다.

```php
$this->forge->addForeignKey('board_id', 'boards', 'id', '', 'CASCASE');
```

```sql
CREATE TABLE `tmp_fk_typo` (
  `id` int unsigned NOT NULL AUTO_INCREMENT,
  `board_id` int unsigned NOT NULL,
  PRIMARY KEY (`id`),
  KEY `tmp_fk_typo_board_id_foreign` (`board_id`),
  CONSTRAINT `tmp_fk_typo_board_id_foreign` FOREIGN KEY (`board_id`) REFERENCES `boards` (`id`)
) ENGINE=InnoDB
```

**에러가 나지 않습니다.** 마이그레이션은 성공하고, 외래 키도 걸리고, 다만 `ON DELETE` 절만 사라졌습니다. 그 결과 `CASCADE` 를 의도한 자리가 바로 위의 기본 동작으로 떨어집니다 — 게시판을 지우려 하면 거절당하는 상태가 됩니다. 의도와 정반대인데 아무도 알려주지 않습니다. 마이그레이션을 돌린 다음 `SHOW CREATE TABLE` 로 한 번 확인하는 습관이 여기서 값을 합니다.

마지막 인자를 생략하면 이름은 `{테이블}_{컬럼}_foreign` 으로 자동으로 붙습니다. 위 실험의 `tmp_fk_typo_board_id_foreign` 이 그렇게 나온 이름입니다. 이 강좌는 `fk_posts_board` 처럼 직접 이름을 줍니다. 나중에 제약을 지우거나 바꿀 때 이름으로 지목해야 하는데, 짧고 규칙적인 쪽이 다루기 편합니다.

### 정말 걸렸는지 확인

없는 게시판을 가리키는 글을 넣어 봅니다.

```sql
INSERT INTO posts (board_id, title, content, created_at, updated_at)
VALUES (99, '없는 게시판', '본문', NOW(), NOW());
```

```
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails
(`ci4board`.`posts`, CONSTRAINT `fk_posts_board` FOREIGN KEY (`board_id`) REFERENCES `boards` (`id`) ON DELETE CASCADE)
```

30편에서 게시판을 지우는 관리자 화면을 만들 때, 이 제약이 없으면 주인 없는 글이 조용히 쌓입니다. 목록에도 안 나오고 지울 방법도 마땅치 않은 행들입니다.

### `SET NULL` — 탈퇴해도 글은 남는다

확인을 위해 게시판 둘, 회원 둘, 글 500건을 넣어 두고 시작합니다. 6편에서 시더로 제대로 만들 테니 여기서는 SQL 한 방으로 때웁니다.

```sql
INSERT INTO posts (board_id, user_id, title, content, is_notice, created_at, updated_at)
WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 500)
SELECT IF(n % 3 = 0, 1, 2),
       IF(n % 5 = 0, NULL, IF(n % 2 = 0, 1, 2)),
       CONCAT('테스트 글 ', n), CONCAT('본문 ', n),
       IF(n % 100 = 0, 1, 0), NOW(), NOW()
FROM seq;
```

1번 회원이 쓴 글이 200건입니다. 그 회원을 지웁니다.

```sql
SELECT COUNT(*) FROM posts WHERE user_id = 1;   -- 200

DELETE FROM users WHERE id = 1;

SELECT COUNT(*) FROM posts WHERE user_id = 1;      -- 0
SELECT COUNT(*) FROM posts WHERE user_id IS NULL;  -- 300
```

글은 한 건도 사라지지 않았습니다. 200건의 `user_id` 가 `NULL` 로 바뀌었을 뿐입니다(원래 `NULL` 이던 비회원 글 100건과 합쳐 300건).

회원을 지웠다고 그 사람이 3년 동안 쓴 답변이 게시판에서 사라지면 곤란합니다. 남은 글은 화면에 "탈퇴한 회원"으로 표시합니다 — 비회원 글과 같은 처리라 코드가 하나로 끝납니다.

### `CASCADE` — 게시판을 지우면 연쇄한다

반대쪽입니다. 2번 게시판에는 글 334건이 있고, 그중 한 글에 댓글 하나와 첨부 하나가 달려 있고, 아직 글에 붙지 않은 임시 업로드도 하나 있습니다.

```sql

       (SELECT COUNT(*) FROM comments)    AS comments_all,
       (SELECT COUNT(*) FROM attachments) AS files_all;
```

```

```

게시판을 지웁니다. 한 줄입니다.

```sql
DELETE FROM boards WHERE id = 2;
```

```
posts_b2  comments_all  files_all
0         0             0
```

`boards` 행 하나를 지웠는데 `posts` 334건이 따라 사라지고, 그 글에 달린 댓글이 다시 따라 사라졌습니다. **연쇄가 두 단계 이어집니다** — `boards` → `posts` → `comments`. 첨부도 마찬가지고, 글에 붙지 않았던 임시 업로드까지 사라졌습니다(그 이유는 4절에서).

이게 3편 8절의 "게시판 없는 글은 갈 곳이 없다"입니다. 다만 실제로 돌려 보면 한 줄의 `DELETE` 가 얼마나 크게 번지는지가 체감됩니다. 30편 관리자 화면에서 게시판 삭제 버튼 옆에 `is_active` 토글을 같이 두기로 한 게 이래서입니다.

### `depth` — 두 번째 층에서 멈춘다

`depth` 는 원 댓글이 0, 대댓글이 1입니다. `parent_id` 가 이미 관계를 담고 있으니 중복인데, 목록을 그릴 때 들여쓰기 단계를 바로 알 수 있어서 뒀습니다.

이 강좌는 **`depth` 를 1까지만** 씁니다. 무제한 계층은 화면이 옆으로 흘러가고, 목록 쿼리도 재귀가 필요해집니다. 게시판에서 실제로 필요한 건 "누구의 말에 대한 답인가" 한 단계까지입니다. 애플리케이션에서 `depth = 1` 인 댓글에는 답글 버튼을 그리지 않는 것으로 제한합니다(23편).

### `idx_post_thread` — `(post_id, parent_id, id)`

상세 화면의 댓글 조회는 `WHERE post_id = ?` 로 시작해서 원 댓글과 대댓글을 묶어 정렬합니다. 4편에서 본 규칙 그대로 — 같음 비교로 좁히는 컬럼이 앞(`post_id`), 묶고 정렬하는 컬럼이 뒤(`parent_id`, `id`) 입니다.

`original_name` 은 사용자가 올린 파일의 원래 이름("2026년 예산안.xlsx"), `stored_name` 은 디스크에 실제로 저장한 이름("a1b2c3d4....xlsx")입니다.

원래 이름 그대로 저장하면 문제가 세 가지 생깁니다. 같은 이름을 올렸을 때 덮어쓰고, 한글·공백·특수문자가 서버마다 다르게 깨지고, `../` 같은 문자열이 섞여 들어오면 의도하지 않은 경로에 파일이 쓰입니다. 그래서 저장은 안전한 임의 이름으로 하고, 화면에 보여주고 내려줄 때만 원래 이름을 씁니다. 24편의 주제입니다.

### `post_id` 가 `NULL` 일 수 있다

이 테이블에서 가장 눈에 띄는 결정입니다. 첨부인데 어느 글의 첨부인지 모르는 행이 허용됩니다.

업로드 순서를 생각하면 자연스럽습니다. 사용자는 글쓰기 화면에서 **파일을 먼저 고릅니다.** 파일은 그 자리에서 서버로 올라가는데, 글은 아직 저장 버튼을 누르기 전이라 `post_id` 가 존재하지 않습니다. 글을 저장하는 순간 그 번호를 채워 넣습니다.

그래서 `post_id IS NULL` 인 행은 **아직 글에 붙지 않은 임시 업로드**입니다. 사용자가 파일만 올려두고 글쓰기를 그만두면 그대로 남습니다. 이 행들을 주기적으로 청소해야 하고, 그 조건이 이렇습니다.

```sql
WHERE post_id IS NULL AND created_at < ?
```

`idx_created` 는 그 청소를 위한 인덱스입니다. 다른 용도가 없습니다.

### `board_id` 를 왜 따로 들고 있나

글을 통해 게시판을 알 수 있으니 중복으로 보입니다. 이유가 둘입니다.

첫째, **`post_id` 가 `NULL` 인 동안에도 소속을 알아야 합니다.** 임시 업로드에도 게시판별 용량·확장자 정책을 적용해야 하는데, 글이 없으면 어느 게시판 규칙을 볼지 알 수 없습니다.

둘째, 2절 마지막의 그 장면입니다. 게시판을 지웠을 때 임시 업로드까지 함께 사라진 건 `fk_attachments_board` 덕분입니다. `post_id` 로만 연결돼 있었다면 글이 없는 그 행들은 살아남아, 어느 게시판 것인지도 모르는 채 디스크를 차지했을 겁니다.

### `deleted_at` 이 없다

`posts` 와 `comments` 에는 있는데 여기는 없습니다. 3편 8절에서 정한 그대로입니다.

첨부는 지울 때 **디스크의 실제 파일도 함께 지워야** 합니다. 파일을 지운 뒤에 행만 남겨두면 되살릴 수 없는데도 살아 있는 척하는 데이터가 됩니다. 목록에는 파일이 보이는데 눌러보면 없는 상태가 그렇게 생깁니다.

## 5. 인덱스를 셋 걸었는데 넷이 생겼다

세 테이블을 만들고 `SHOW CREATE TABLE` 로 확인해 봅니다. `posts` 부터입니다.

```sql
SHOW CREATE TABLE posts;
```

```sql
CREATE TABLE `posts` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `board_id` int unsigned NOT NULL,
  `user_id` bigint unsigned DEFAULT NULL,
  ...
  `ip` varbinary(16) DEFAULT NULL,
  `created_at` datetime DEFAULT NULL,
  `updated_at` datetime DEFAULT NULL,
  `deleted_at` datetime DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_board_list` (`board_id`,`deleted_at`,`is_notice`,`id`),
  KEY `idx_board_created` (`board_id`,`created_at`),
  KEY `idx_user` (`user_id`,`id`),
  CONSTRAINT `fk_posts_board` FOREIGN KEY (`board_id`) REFERENCES `boards` (`id`) ON DELETE CASCADE,
  CONSTRAINT `fk_posts_user` FOREIGN KEY (`user_id`) REFERENCES `users` (`id`) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
```

건 대로 나왔습니다. 인덱스 셋, 외래 키 둘. 그런데 `comments` 는 다릅니다.

```sql
  PRIMARY KEY (`id`),
  KEY `fk_comments_parent` (`parent_id`),      ← 만든 적 없는 인덱스
  KEY `idx_post_thread` (`post_id`,`parent_id`,`id`),
  KEY `idx_user` (`user_id`,`id`),
  CONSTRAINT `fk_comments_parent` FOREIGN KEY (`parent_id`) REFERENCES `comments` (`id`) ON DELETE CASCADE,
  ...
```

인덱스를 둘 걸었는데 셋입니다. `attachments` 도 같습니다 — `KEY fk_attachments_board (board_id)` 가 저절로 생겼습니다.

**InnoDB 는 외래 키 컬럼에 인덱스가 없으면 스스로 만듭니다.** 참조 무결성을 확인하려면 그 컬럼으로 조회할 수 있어야 하는데, 인덱스가 없으면 매번 테이블 전체를 훑어야 하기 때문입니다.

여기서 규칙이 하나 보입니다. **이미 있는 인덱스의 맨 앞 컬럼이면 새로 만들지 않습니다.**

| 테이블 | FK 컬럼 | 기존 인덱스 | 자동 생성 |
|---|---|---|---|
| `posts` | `board_id` | `idx_board_list` 의 첫 컬럼 | 안 함 |
| `posts` | `user_id` | `idx_user` 의 첫 컬럼 | 안 함 |
| `comments` | `post_id` | `idx_post_thread` 의 첫 컬럼 | 안 함 |
| `comments` | `parent_id` | 어느 인덱스에서도 첫 컬럼이 아님 | **함** |
| `attachments` | `post_id` | `idx_post_sort` 의 첫 컬럼 | 안 함 |
| `attachments` | `board_id` | 어느 인덱스에서도 첫 컬럼이 아님 | **함** |

`comments.parent_id` 는 `idx_post_thread` 안에 들어 있긴 합니다. 하지만 두 번째 자리라 `parent_id` 만으로 찾는 데는 못 씁니다. 인덱스는 앞에서부터 순서대로 읽는 자료구조라, 첫 컬럼 조건이 없으면 뒤 컬럼만 골라 쓸 수 없습니다.

그래서 **인덱스를 설계할 때 외래 키 컬럼을 맨 앞에 두면 인덱스 하나를 아낍니다.** `posts` 의 셋이 전부 그 모양인 건 우연이 아닙니다. 인덱스는 공짜가 아니라 쓰기마다 갱신 비용을 내는 물건이라, 같은 값을 하는 인덱스가 둘 생기지 않게 하는 편이 좋습니다.

## 6. `EXPLAIN` — 인덱스가 정말 일하는가

3편에서 `idx_board_list` 의 컬럼 순서를 길게 설명했습니다. 그 설계가 맞았는지는 `EXPLAIN` 으로만 알 수 있습니다.

2절에서 넣어둔 500건이 그대로 있는 상태입니다. 9편에서 만들 목록 쿼리를 미리 던져 봅니다.

```sql
EXPLAIN SELECT id, title, created_at FROM posts
 WHERE board_id = 2 AND deleted_at IS NULL
 ORDER BY is_notice DESC, id DESC
 LIMIT 20\G
```

```
           type: ref
  possible_keys: idx_board_list,idx_board_created
            key: idx_board_list
        key_len: 10
            ref: const,const
           rows: 334
          Extra: Using where; Backward index scan
```

읽을 곳은 셋입니다.

- **`key: idx_board_list`** — 의도한 인덱스를 골랐습니다.
- **`ref: const,const`** — 상수 둘로 범위를 좁혔습니다. `board_id = 2` 와 `deleted_at IS NULL` 입니다. `IS NULL` 도 인덱스가 처리한다는 게 보입니다.
- **`Backward index scan`** — 인덱스를 뒤에서부터 읽었습니다. 3편에서 "`DESC` 인덱스를 안 만들어도 된다"고 한 근거가 이 한 줄입니다.

그리고 **`Using filesort` 가 없습니다.** 정렬을 따로 하지 않았다는 뜻입니다. 인덱스에 이미 `is_notice, id` 순으로 정렬돼 있으니 그대로 스무 건 읽고 멈추면 됩니다.

비교를 위해 조건을 바꿔 세 번 더 던져 봤습니다.

| 쿼리 | key | Extra |
|---|---|---|
| `SELECT id` (제목 없이) | `idx_board_list` | `Backward index scan; Using index` |
| `ORDER BY view_count DESC` | `idx_board_list` | `Using index condition; Using filesort` |
| `board_id` 조건 없이 | **NULL** | `Using where; Using filesort` (`type: ALL`) |

첫 줄의 **`Using index`** 는 커버링 인덱스가 걸렸다는 뜻입니다. `id` 만 필요하면 인덱스 안에 답이 다 있어서 테이블 데이터를 아예 읽지 않습니다. 맨 위 쿼리에 이게 없는 건 `title`, `created_at` 을 가지러 테이블에 다녀오기 때문입니다.

둘째 줄은 정렬 컬럼이 인덱스에 없을 때입니다. `view_count` 로 정렬하라고 하면 334건을 다 꺼내 놓고 따로 정렬합니다(`Using filesort`). 조회수순 정렬을 26편에서 옵션으로 넣을 텐데, 그때 이 비용을 다시 이야기합니다.

셋째 줄이 인덱스가 완전히 죽는 자리입니다. 첫 컬럼인 `board_id` 조건이 빠지자 `key` 가 `NULL` 이 되고 `type: ALL` — 500건 전부를 훑습니다. 5절에서 "첫 컬럼 조건이 없으면 뒤 컬럼만 골라 쓸 수 없다"고 한 것이 실제로 이렇게 나타납니다.

> 지금은 500건이라 어느 쪽이든 눈 깜짝할 사이입니다. 인덱스 이야기를 이 시점에 하는 이유는 **느려진 뒤에는 이 판단을 다시 하기 어렵기 때문**입니다. 데이터가 쌓인 테이블에 인덱스를 새로 거는 일은 시간도 잠금도 감수해야 하는 작업입니다.

## 7. 소프트 딜리트는 DB가 모른다

`posts.deleted_at` 과 `comments.deleted_at` 을 만들었습니다. 여기에 대한 오해를 하나 풀고 갑니다.

**이 컬럼은 그냥 `DATETIME` 입니다.** MySQL 은 이 이름에 아무 의미를 두지 않습니다. 외래 키도, `CASCADE` 도 이 컬럼을 보지 않습니다.

확인해 봤습니다. 1번 글에 댓글 둘과 첨부 하나를 달아 둔 상태에서, 그 글을 소프트 딜리트합니다.

```sql
UPDATE posts SET deleted_at = NOW() WHERE id = 1;

SELECT (SELECT COUNT(*) FROM comments    WHERE post_id = 1) AS comments_left,
       (SELECT COUNT(*) FROM attachments WHERE post_id = 1) AS files_left;
```

```
comments_left  files_left
2              1
```

아무 일도 일어나지 않았습니다. 댓글도 첨부도 그대로입니다. 2절에서 `DELETE` 한 줄에 수백 건이 연쇄한 것과 대조적입니다.

여기서 두 가지가 따라옵니다.

**하나. 지워진 글을 걸러내는 건 애플리케이션의 책임입니다.** 앞으로 `posts` 를 읽는 모든 쿼리에 `deleted_at IS NULL` 이 따라붙어야 합니다. 한 군데라도 빠뜨리면 지운 글이 목록에 나타납니다. 그래서 CodeIgniter Model 에 그 일을 맡깁니다.

```php
// app/Models/PostModel.php — 9편에서 만듭니다
protected $useSoftDeletes = true;
protected $deletedField   = 'deleted_at';
```

이렇게 두면 Model 을 거치는 조회에는 조건이 자동으로 붙고, `delete()` 는 `DELETE` 대신 `UPDATE` 를 날립니다. 다만 **Model 을 거치지 않는 경로에는 아무 효과가 없습니다** — 직접 쓴 Query Builder 쿼리, 시더, 관리자 일괄 처리가 그렇습니다.

**둘. `idx_board_list` 의 두 번째 컬럼이 `deleted_at` 인 이유가 이것입니다.**

```
(board_id, deleted_at, is_notice, id)
```

모든 목록 쿼리에 `deleted_at IS NULL` 이 붙는다면, 그 조건은 사실상 `board_id` 와 한 몸입니다. 앞의 `EXPLAIN` 에서 `ref: const,const` 로 둘이 함께 잡힌 게 그 결과입니다. 소프트 딜리트를 쓰기로 한 결정이 인덱스 설계까지 바꿔 놓는 자리입니다.

그리고 12편의 질문 — 글을 소프트 딜리트하면 그 댓글은? — 에 대한 DB 쪽 답이 방금 나왔습니다. **아무 일도 일어나지 않습니다.** 무엇을 할지는 그 편에서 정합니다.

### 왜 되돌리기가 역순이어야 하는가

4편에서 롤백이 역순으로 돈다는 걸 봤습니다. 그때는 두 테이블 사이에 관계가 없어서 "그렇구나" 하고 넘어갔습니다. 이번에는 그 순서가 **지켜지지 않으면 실패합니다.**

`posts` 가 살아 있는 상태에서 `boards` 를 지워 보면 이렇습니다.

```sql
DROP TABLE boards;
```

```
ERROR 3730 (HY000): Cannot drop table 'boards' referenced by a foreign key constraint 'fk_posts_board' on table 'posts'.
```

가리키는 쪽이 남아 있는 한 가리켜지는 쪽은 지워지지 않습니다. 그래서 만드는 순서와 지우는 순서가 반대여야 합니다.

```bash
php spark migrate:rollback
```

```
Rolling back migrations to batch:  1
	Rolling back: (App) 2026-08-11-000005_App\Database\Migrations\CreateAttachmentsTable
	Rolling back: (App) 2026-08-11-000004_App\Database\Migrations\CreateCommentsTable
	Rolling back: (App) 2026-08-11-000003_App\Database\Migrations\CreatePostsTable
Done rolling back migrations.
```

`attachments` → `comments` → `posts`. 만든 순서를 정확히 거꾸로 되짚었고, 그래서 FK 에 걸리지 않았습니다.

이번에는 4편과 달리 **1번 묶음까지만** 되돌아갔습니다(`to batch: 1`). 인자 없는 `rollback` 은 마지막 묶음 하나만 되돌리는데, 이제 묶음이 둘이라 차이가 드러납니다. `users` 와 `boards` 는 그대로 남아 있습니다.

```
| App       | 2026-08-11-000003 | CreatePostsTable       | ---     | ---                 | ---   |
| App       | 2026-08-11-000004 | CreateCommentsTable    | ---     | ---                 | ---   |
| App       | 2026-08-11-000005 | CreateAttachmentsTable | ---     | ---                 | ---   |
```

되돌린 줄은 `Batch` 가 `---` 로 바뀝니다. 파일은 그대로 있고 적용만 취소된 상태입니다. 확인이 끝났으면 다시 올려 둡니다.

```bash
php spark migrate
```

## 마무리

3편에서 그린 여덟 개 중 다섯이 섰습니다. 뼈대는 여기까지입니다.

이번 편의 절반은 실제로 지워 보는 데 썼습니다. 외래 키는 마이그레이션에 적을 때는 한 줄이지만, 그 한 줄이 정하는 것은 **사고가 났을 때 무엇이 남아 있느냐**입니다. 회원을 지웠는데 3년치 글이 사라졌다는 이야기가 나오는 자리가 여기고, 그 차이가 `SET NULL` 과 `CASCADE` 라는 단어 하나였습니다.

다음 회차에서는 이 빈 테이블에 데이터를 붓습니다. Faker 로 게시판 세 개와 글 200건을 만드는 시더입니다. 이번 편에서 500건을 SQL 로 우겨넣은 걸 제대로 다시 합니다. 그리고 왜 `mysql` 명령줄이 아니라 CI4 시더로 하는지 — 한글이 이중 인코딩되어 화면에는 멀쩡해 보이는 사고를 하나 보여드리겠습니다.
