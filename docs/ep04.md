지난 편에서 테이블 여덟 개를 그렸습니다. 그림까지만 그렸고 DB는 아직 비어 있습니다.

이번 편에서 그중 둘을 실제로 만듭니다. `users` 와 `boards` 입니다. 그러면서 지난 편에서 미뤄둔 숙제를 갚습니다 — **`boards` 의 컬럼 스물두 개가 각각 왜 필요한지.**

이 강좌에서 코드가 나오는 첫 편입니다.

---

## 1. 순서가 곧 의존성

다음 편에서 만들 `posts` 는 `board_id` 로 `boards` 를, `user_id` 로 `users` 를 참조합니다. 외래 키는 가리키는 대상이 이미 있어야 걸리므로, 참조당하는 쪽이 먼저입니다.

마이그레이션의 실행 순서는 **파일 이름**이 정합니다. CodeIgniter는 `app/Database/Migrations/` 안의 파일을 이름순으로 정렬해 앞에서부터 실행합니다. 클래스 이름도, 파일을 만든 시각도 보지 않습니다.

빈 파일은 이 명령으로 만듭니다.

```bash
php spark make:migration CreateUsersTable
```

```
File created: APPPATH/Database/Migrations/2026-08-24-010854_CreateUsersTable.php
```

앞에 붙은 숫자는 명령을 실행한 시각입니다. 다만 이 강좌의 저장소에서는 그 자리를 손으로 매겼습니다.

```
2026-08-11-000001_CreateUsersTable.php
2026-08-11-000002_CreateBoardsTable.php
```

스키마 전체를 3편에서 확정해 뒀으니 순번이 눈에 보이는 편이 낫다고 봤습니다. 여러분 프로젝트에서는 `make:migration` 이 준 이름을 그냥 쓰셔도 됩니다. 여럿이 작업한다면 오히려 그쪽이 안전합니다 — 시각이 들어 있으면 두 사람이 같은 날 만들어도 이름이 겹치지 않습니다.

## 2. `users`

`app/Database/Migrations/2026-08-11-000001_CreateUsersTable.php`

```php
<?php

namespace App\Database\Migrations;

use CodeIgniter\Database\Migration;

class CreateUsersTable extends Migration
{
    public function up(): void
    {
        $this->forge->addField([
            'id'            => ['type' => 'BIGINT', 'unsigned' => true, 'auto_increment' => true],
            'email'         => ['type' => 'VARCHAR', 'constraint' => 190],
            'username'      => ['type' => 'VARCHAR', 'constraint' => 50],
            'nickname'      => ['type' => 'VARCHAR', 'constraint' => 50],
            'password_hash' => ['type' => 'VARCHAR', 'constraint' => 255],
            'level'         => ['type' => 'TINYINT', 'unsigned' => true, 'default' => 1],
            'role'          => ['type' => 'ENUM', 'constraint' => ['member', 'manager', 'admin'], 'default' => 'member'],
            'status'        => ['type' => 'ENUM', 'constraint' => ['active', 'dormant', 'suspended'], 'default' => 'active'],
            'last_login_at' => ['type' => 'DATETIME', 'null' => true],
            'created_at'    => ['type' => 'DATETIME', 'null' => true],
            'updated_at'    => ['type' => 'DATETIME', 'null' => true],
        ]);

        $this->forge->addPrimaryKey('id');
        $this->forge->addUniqueKey('email');
        $this->forge->addUniqueKey('username');
        $this->forge->createTable('users');
    }

    public function down(): void
    {
        $this->forge->dropTable('users', true);
    }
}
```

`$this->forge` 는 CodeIgniter가 마이그레이션 클래스에 미리 넣어주는 객체입니다. 배열로 테이블을 서술하면 접속 중인 DB에 맞는 `CREATE TABLE` 을 만들어 줍니다.

### `email` 이 왜 190인가

이메일 규격상 최대 길이는 254자입니다. 190은 **인덱스 키 길이 제한**에서 나온 숫자입니다.

`email` 에는 UNIQUE 인덱스가 걸립니다. `utf8mb4` 는 한 글자가 최대 4바이트이므로 `VARCHAR(255)` 는 1020바이트를 예약하는데, InnoDB의 옛 행 포맷(`COMPACT`, `REDUNDANT`)에서는 인덱스 하나의 상한이 767바이트입니다.

```sql
CREATE TABLE t (email VARCHAR(255) NOT NULL, UNIQUE KEY (email))
  ENGINE=InnoDB ROW_FORMAT=COMPACT DEFAULT CHARSET=utf8mb4;
```

```
ERROR 1071 (42000): Specified key was too long; max key length is 767 bytes
```

190이면 760바이트라 턱걸이로 통과합니다. 예전 MySQL이나 MariaDB에서 이 에러를 만나 본 분이 많을 겁니다. 지금은 기본 행 포맷이 `DYNAMIC` 이고 상한이 3072바이트라 `VARCHAR(255)` 도 그냥 들어갑니다.

그러니 190은 **지금은 필요 없는 안전장치**입니다. 그래도 두는 이유는 이 프로젝트가 어디에 배포될지 모르기 때문입니다. 오래된 MySQL이 깔린 호스팅에 올라가는 순간 이 컬럼 하나 때문에 마이그레이션 전체가 멈춥니다.

### `username` 과 `nickname`

둘 다 `VARCHAR(50)` 인데 하나만 UNIQUE 입니다.

| 컬럼 | UNIQUE | 쓰이는 곳 |
|---|---|---|
| `username` | O | URL에 들어갈 고유 식별자. 잘 바꾸지 않는다 |
| `nickname` | X | 화면에 보이는 이름. 언제든 바꾼다 |

`nickname` 에 UNIQUE를 걸지 않은 건 선택입니다. 표시 이름이 겹쳐도 `username` 으로 구분되니 괜찮다고 봤습니다. 사칭이 신경 쓰이는 서비스라면 UNIQUE를 하나 더 걸면 됩니다 — 스키마를 바꾸는 게 아니라 인덱스만 추가하는 일이라 부담이 적습니다.

### `password_hash` 는 왜 255인가

`password_hash()` 가 bcrypt로 만드는 해시는 60자입니다. 60이면 충분해 보이는데, `PASSWORD_DEFAULT` 는 "지금 권장되는 알고리즘"이라는 뜻이라 **언젠가 바뀝니다.** PHP 7.2에 들어온 Argon2 계열은 해시가 90자를 넘습니다.

컬럼을 60으로 잡아둔 프로젝트는 그 기본값이 바뀌는 날부터 잘린 해시를 저장하기 시작합니다. **로그인이 안 되는데 에러는 안 납니다.** PHP 매뉴얼이 255를 권하는 이유입니다. `VARCHAR` 는 실제로 쓴 만큼만 저장하므로 넉넉히 잡아도 낭비가 아닙니다.

### `level` 과 `role` 이 겹치지 않나

겹칩니다. 그래도 나눈 이유가 있습니다.

`level` 은 **비교하는 값**입니다. `boards` 에 `read_level`, `write_level` 같은 문턱값이 있고 판정은 `사용자 level >= 게시판 요구 level` 한 줄입니다. 게시판마다 문턱을 다르게 두려면 값이 연속이어야 하고, 그래서 숫자입니다.

`role` 은 **가르는 값**입니다. 관리자 화면에 들어갈 수 있는가. 이건 정도가 아니라 자격의 문제라 `role === 'admin'` 이 `level >= 10` 보다 읽기 좋고, 나중에 레벨 체계를 손봐도 안 깨집니다.

하나로 합칠 수도 있지만 그러면 둘 중 하나는 억지가 됩니다. 16편에서 게시판별 레벨 판정을, 17편에서 Policy 클래스가 둘을 어떻게 조합하는지 봅니다.

그리고 **`level = 0` 인 행은 이 테이블에 들어가지 않습니다.** 0은 로그인하지 않은 방문자의 값입니다. 굳이 정의해 둔 건 판정 코드를 하나로 만들기 위해서입니다 — 비회원 레벨을 0으로 놓으면 로그인 여부를 따로 묻지 않고 `level >= read_level` 로 끝납니다.

### `created_at` 이 왜 `NULL` 허용인가

생성 시각이 없는 행은 없을 텐데 `NULL` 을 허용했습니다. Model이 `$useTimestamps = true` 일 때 이 컬럼을 채워주지만, Model을 거치지 않는 경로가 있기 때문입니다 — 시더, 관리자 일괄 처리, 직접 쓴 SQL. `NOT NULL` 에 기본값도 없으면 그때마다 에러가 납니다.

## 3. `boards` — 컬럼 스물두 개

3편에서 이 테이블을 "데이터를 담는 곳이 아니라 설정을 담는 곳"이라고 했습니다. 이제 그 설정을 하나씩 봅니다.

`app/Database/Migrations/2026-08-11-000002_CreateBoardsTable.php`

```php
public function up(): void
{
    $this->forge->addField([
        'id'          => ['type' => 'INT', 'unsigned' => true, 'auto_increment' => true],
        'slug'        => ['type' => 'VARCHAR', 'constraint' => 50],
        'name'        => ['type' => 'VARCHAR', 'constraint' => 100],
        'description' => ['type' => 'VARCHAR', 'constraint' => 255, 'null' => true],
        'skin'        => ['type' => 'ENUM', 'constraint' => ['list', 'gallery', 'faq'], 'default' => 'list'],
        'per_page'    => ['type' => 'SMALLINT', 'unsigned' => true, 'default' => 20],
        'categories'  => ['type' => 'JSON', 'null' => true],

        'use_comment' => ['type' => 'TINYINT', 'constraint' => 1, 'default' => 1],
        'use_file'    => ['type' => 'TINYINT', 'constraint' => 1, 'default' => 1],
        'use_secret'  => ['type' => 'TINYINT', 'constraint' => 1, 'default' => 0],
        'use_editor'  => ['type' => 'TINYINT', 'constraint' => 1, 'default' => 0],

        'max_files'     => ['type' => 'TINYINT', 'unsigned' => true, 'default' => 5],
        'max_file_size' => ['type' => 'INT', 'unsigned' => true, 'default' => 5242880],
        'allowed_ext'   => ['type' => 'VARCHAR', 'constraint' => 255, 'default' => 'jpg,jpeg,png,gif,webp,pdf,zip'],

        'read_level'     => ['type' => 'TINYINT', 'unsigned' => true, 'default' => 0],
        'write_level'    => ['type' => 'TINYINT', 'unsigned' => true, 'default' => 1],
        'comment_level'  => ['type' => 'TINYINT', 'unsigned' => true, 'default' => 1],
        'download_level' => ['type' => 'TINYINT', 'unsigned' => true, 'default' => 1],

        'sort_order' => ['type' => 'SMALLINT', 'default' => 0],
        'is_active'  => ['type' => 'TINYINT', 'constraint' => 1, 'default' => 1],
        'created_at' => ['type' => 'DATETIME', 'null' => true],
        'updated_at' => ['type' => 'DATETIME', 'null' => true],
    ]);

    $this->forge->addPrimaryKey('id');
    $this->forge->addUniqueKey('slug');
    $this->forge->addKey(['is_active', 'sort_order'], false, false, 'idx_active_sort');
    $this->forge->createTable('boards');
}
```

배열에 빈 줄을 넣어 나눈 덩어리가 그대로 설명 단위입니다.

### ① 신원 — `id`, `slug`, `name`, `description`

`slug` 가 이 테이블에서 가장 중요한 컬럼입니다. 7편에서 만들 라우트가 `/board/{slug}` 하나뿐이라, 주소로 들어온 문자열을 이 컬럼에서 찾는 것이 모든 요청의 첫 동작이 됩니다. UNIQUE인 이유도 그래서입니다 — 같은 slug가 둘이면 어느 게시판을 열어야 할지 알 수 없습니다. `name` 은 화면에 보이는 이름("공지사항"), `description` 은 상단 안내문입니다.

`id` 만 `BIGINT` 가 아니라 `INT` 입니다. 게시판이 42억 개가 될 일은 없습니다. `posts.id` 가 `BIGINT` 인 건 글은 그럴 수도 있기 때문입니다.

### ② 표현 — `skin`, `per_page`, `categories`

| 컬럼 | 하는 일 |
|---|---|
| `skin` | `list` / `gallery` / `faq`. 목록을 어떤 모양으로 그릴지 (28편) |
| `per_page` | 한 페이지에 몇 건 (9편) |
| `categories` | 게시판 안의 분류 배열. JSON |

`skin` 을 ENUM으로 잡은 게 걸릴 수 있습니다. 3편에서 `categories` 는 `ALTER` 를 피하려고 JSON으로 갔는데, 여기서는 값 하나 늘리는 데 `ALTER TABLE` 이 필요하니까요.

기준이 다릅니다. **스킨을 하나 늘리려면 뷰 파일을 새로 만들어야 합니다.** 코드 배포가 어차피 따라오는 작업이라 마이그레이션을 같이 내보내는 게 부담이 아닙니다. 반면 카테고리는 관리자가 화면에서 만드는 값입니다. 그걸 추가하겠다고 배포를 시킬 수는 없습니다.

**DB 구조를 바꾸는 변경인가, 운영자가 평소에 하는 변경인가.** 이 답이 ENUM과 JSON을 가릅니다. 앞에 나온 `role`, `status` 도 같은 기준입니다.

### ③ 기능 토글 — `use_*` 넷

| 컬럼 | 기본값 | 켜면 |
|---|---|---|
| `use_comment` | 1 | 댓글 (22편) |
| `use_file` | 1 | 파일 첨부 (24편) |
| `use_secret` | 0 | 비밀글 (27편) |
| `use_editor` | 0 | 위지윅 에디터 (25편). 그전까지는 `<textarea>` |

공지사항에는 댓글을 막고 문의 게시판에는 비밀글을 켭니다. 이게 게시판마다 달라야 한다는 것이 이 프로젝트의 출발점이었습니다.

기본값이 갈리는 게 보입니다. 댓글과 첨부는 켜져 있고, 비밀글과 에디터는 꺼져 있습니다. **게시판을 새로 만들었을 때 대부분 원하는 상태**를 기본값으로 잡았습니다.

### ④ 업로드 정책 — `max_files`, `max_file_size`, `allowed_ext`

크기를 바이트로 둔 건 계산 없이 바로 비교하기 위해서입니다(5242880 = 5MB). "5MB" 같은 표시는 화면에서 만듭니다.

`allowed_ext` 는 쉼표로 이어붙인 문자열입니다. 3편에서 `categories` 를 JSON으로 둘 때와 같은 상황인데 — 항상 통째로 읽고 통째로 씁니다 — 값이 짧고 단순해서 문자열로 뒀습니다.

한 가지 미리 짚어둡니다. **확장자 목록은 보안 장치가 아닙니다.** `.jpg` 로 이름만 바꾼 PHP 파일은 이 검사를 그냥 통과합니다. 실제 방어는 24편에서 파일 내용을 보는 MIME 검사와 웹루트 밖 저장으로 합니다. `allowed_ext` 는 "이 게시판은 이미지랑 PDF만 올리는 곳"이라는 **운영 규칙**에 가깝습니다.

### ⑤ 권한 — `*_level` 넷

| 컬럼 | 기본값 | 뜻 |
|---|---|---|
| `read_level` | 0 | 읽기. 0이라 비회원도 본다 |
| `write_level` | 1 | 글쓰기. 로그인해야 한다 |
| `comment_level` | 1 | 댓글 |
| `download_level` | 1 | 첨부 다운로드 |

2절의 `users.level` 과 비교되는 값입니다. 판정은 `사용자 level >= 이 값`.

넷으로 나눈 이유는 실제로 따로 놀기 때문입니다. 자료실을 떠올리면 됩니다 — 목록과 본문은 누구나 보되(`read_level = 0`), 파일은 로그인한 사람만 받게(`download_level = 1`) 하는 조합이 흔합니다. 하나로 합쳐두면 이게 안 됩니다.

기본값 조합이 곧 "보통의 게시판"입니다. 누구나 읽고, 회원만 씁니다.

### ⑥ 운영 — `sort_order`, `is_active`

`sort_order` 에는 `unsigned` 를 붙이지 않았습니다. 음수를 쓸 수 있으면 이미 순서가 잡힌 목록에서 하나를 맨 앞으로 보낼 때 `-1` 만 주면 됩니다. 다른 행을 건드리지 않아도 됩니다.

`is_active` 는 게시판에 거는 소프트 딜리트입니다. 게시판을 지우면 3편 8절의 규칙대로 그 안의 글이 전부 `CASCADE` 로 사라집니다. 되돌릴 수 없는 동작이라, 실제로는 "잠시 안 보이게" 로 충분한 경우가 대부분입니다. 30편 관리자 화면에서 삭제 버튼 옆에 이 토글을 같이 둡니다.

### 인덱스와 `addKey`

마지막 세 줄의 `addKey` 는 인자가 불친절합니다. `false, false` 만 봐서는 무엇을 껐는지 알 수 없습니다.

```php
addKey($key, $primary = false, $unique = false, $keyName = '')
```

두 번째가 기본 키, 세 번째가 유니크, 네 번째가 인덱스 이름입니다. 그러니 저 줄은 "`is_active` 와 `sort_order` 를 묶은 평범한 인덱스를 `idx_active_sort` 라는 이름으로 만들어라"입니다. `addPrimaryKey` 와 `addUniqueKey` 는 앞의 둘을 미리 채워둔 지름길일 뿐입니다.

컬럼 순서는 3편 6절의 규칙 그대로입니다. **같음 비교로 좁히는 컬럼이 앞, 정렬에 쓰는 컬럼이 뒤.** 목록 쿼리가 `WHERE is_active = 1 ORDER BY sort_order` 모양이기 때문입니다. 게시판이 수십 개뿐이라 체감할 일은 없지만, 여기서부터 지켜두면 `posts` 처럼 무거워지는 테이블에서 헷갈리지 않습니다.

### 여기 없는 컬럼

`field_schema` 가 없습니다. 3편 7절에서 예고한 대로 19편에서 `ALTER TABLE` 로 붙입니다. 이 강좌에서 뒤늦게 컬럼을 추가하는 두 번 중 하나입니다.

## 4. `TINYINT(1)` 의 `1` 은 자릿수가 아니다

`use_comment` 같은 참/거짓 컬럼에 `'constraint' => 1` 이 붙어 `TINYINT(1)` 이 됐습니다.

여기 오해가 하나 있습니다. **괄호 안 숫자는 저장 범위와 아무 상관이 없습니다.** `TINYINT` 는 괄호에 무엇을 쓰든 1바이트를 쓰고 -128~127을 담습니다. `TINYINT(1)` 컬럼에 `100` 을 넣으면 그대로 들어갑니다.

저건 **표시 폭(display width)** 입니다. 값을 몇 칸으로 맞춰 보여줄지에 대한 힌트일 뿐이고, MySQL 8.0.19부터는 폐기 예정으로 지정되어 출력에서 지워집니다. 다섯 컬럼을 각각 다른 폭으로 만들고 다시 읽어 봤습니다.

```sql
CREATE TABLE t_width (
  a TINYINT(1), b TINYINT(4), c INT(11), d SMALLINT(6), e TINYINT UNSIGNED
) ENGINE=InnoDB;

SHOW CREATE TABLE t_width;
```

```sql
CREATE TABLE `t_width` (
  `a` tinyint(1) DEFAULT NULL,
  `b` tinyint DEFAULT NULL,
  `c` int DEFAULT NULL,
  `d` smallint DEFAULT NULL,
  `e` tinyint unsigned DEFAULT NULL
)
```

`tinyint(4)`, `int(11)`, `smallint(6)` 의 폭은 전부 사라졌는데 **`tinyint(1)` 만 남았습니다.**

의도된 예외입니다. `TINYINT(1)` 은 오랫동안 "이건 불리언이다"라는 관례로 쓰였고, 여러 DB 드라이버가 이 표기를 보고 값을 참/거짓으로 바꿔 줍니다. 그래서 다른 폭은 다 지우면서 이것만 남겼습니다.

정리하면 `TINYINT(1)` 은 DB에 거는 제약이 아니라 **읽는 사람과 드라이버에게 남기는 표시**입니다. 0과 1만 들어가게 막는 건 애플리케이션의 몫이고, 30편의 관리자 폼 검증이 그 일을 합니다.

### Forge가 만든 SQL 확인

```sql
SHOW CREATE TABLE boards;
```

```sql
CREATE TABLE `boards` (
  `id` int unsigned NOT NULL AUTO_INCREMENT,
  `slug` varchar(50) COLLATE utf8mb4_unicode_ci NOT NULL,
  ...
  `categories` json DEFAULT NULL,
  `use_comment` tinyint(1) NOT NULL DEFAULT '1',
  ...
  PRIMARY KEY (`id`),
  UNIQUE KEY `slug` (`slug`),
  KEY `idx_active_sort` (`is_active`,`sort_order`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
```

마지막 줄을 보세요. **`COLLATE=utf8mb4_unicode_ci`** 입니다. 2편에서 `.env` 에 적은 두 줄이 값을 하는 자리가 여기입니다. 안 적었다면 DB를 어떻게 만들었든 `utf8mb4_general_ci` 로 나왔을 겁니다.

`categories` 는 `json` 으로 찍혔습니다. MySQL 8의 네이티브 JSON 타입입니다. MariaDB에서 같은 마이그레이션을 돌리면 `longtext` 에 검사 제약이 붙은 형태로 나옵니다. 진행에는 차이가 없고, 그 차이가 언제 드러나는지는 18편에서 봅니다.

### 행 하나 넣어보기

게시판을 하나 만들어 봅니다. 여덟 개 컬럼만 채웁니다.

```sql
INSERT INTO boards (slug, name, description, skin, per_page, categories, created_at, updated_at)
VALUES ('notice', '공지사항', '운영 공지', 'list', 20, JSON_ARRAY('일반', '점검'), NOW(), NOW());

SELECT id, slug, name, categories, use_comment, read_level, write_level, is_active FROM boards;
```

```
id          | 1
slug        | notice
name        | 공지사항
categories  | ["일반", "점검"]
use_comment | 1
read_level  | 0
write_level | 1
is_active   | 1
```

채우지 않은 컬럼 열세 개가 기본값으로 들어찼습니다(`id` 는 auto_increment 가 붙였습니다). 댓글이 켜져 있고, 누구나 읽을 수 있고, 회원만 쓸 수 있는 게시판이 됐습니다.

이 테이블을 설정 테이블이라고 부른 이유가 여기서 보입니다. **기본값 묶음이 곧 "새 게시판의 기본 정책"입니다.** 30편에서 관리자가 폼을 대충 채워도 쓸 만한 게시판이 나오는 건 이 값들 덕분입니다.

`slug` 가 정말 UNIQUE인지도 봅니다.

```sql
INSERT INTO boards (slug, name, created_at, updated_at)
VALUES ('notice', '공지 복제', NOW(), NOW());
```

```
ERROR 1062 (23000): Duplicate entry 'notice' for key 'boards.slug'
```

30편에서 게시판 생성 폼에 검증 규칙도 걸겠지만, 마지막 방어선은 이쪽입니다.

확인이 끝났으면 넣은 행은 지웁니다. 진짜 데이터는 6편 시더로 만듭니다.

```sql
DELETE FROM boards;
```

## 6. 되돌리기 — `down()` 을 진짜로 쓰는 자리

`down()` 은 습관적으로 채우고 한 번도 안 돌려보는 경우가 많습니다. 돌려봅니다.

```bash
php spark migrate:rollback
```

```
Rolling back migrations to batch:  0
	Rolling back: (App) 2026-08-11-000002_App\Database\Migrations\CreateBoardsTable
	Rolling back: (App) 2026-08-11-000001_App\Database\Migrations\CreateUsersTable
Done rolling back migrations.
```

**역순입니다.** `boards` 를 먼저 지우고 `users` 를 지웠습니다. 적용한 순서를 거꾸로 되짚는 것이 CodeIgniter의 규칙입니다.

지금은 두 테이블 사이에 FK가 없어서 어느 쪽을 먼저 지워도 상관없습니다. 하지만 `posts` 가 들어오는 다음 편부터는 이 순서여야만 합니다 — 참조하는 쪽을 남겨두고 참조당하는 쪽을 지울 수는 없으니까요. 마이그레이션 순서를 파일 이름으로 못 박아 두면 되돌릴 때도 자동으로 맞습니다.

확인이 끝났으면 `php spark migrate` 로 다시 올려 둡니다.

왕복을 지금 봐 두는 이유는 이렇습니다. `up()` 만 맞으면 개발 중에는 아무 문제가 없어서, `down()` 이 틀렸다는 건 **정말 되돌려야 하는 상황에서야** 알게 됩니다. 그때는 이미 급합니다.

### `Batch` 가 무엇인가

`migrate:status` 에 있던 열입니다. **`php spark migrate` 한 번에 적용된 묶음**에 같은 번호가 붙습니다. 이 강좌는 회차마다 그 편의 마이그레이션을 돌리므로 대체로 **회차 하나가 batch 하나**가 됩니다.

`migrate:rollback` 은 인자가 없으면 **마지막 batch 하나만** 되돌립니다. 위에서 전부 지워진 건 batch가 1번 하나뿐이었기 때문입니다. 특정 지점으로 돌아가려면 번호를 줍니다.

```bash
php spark migrate:rollback -b 1     # 1번 batch 까지 남기고 되돌린다
php spark migrate:rollback -b 0     # 전부 되돌린다
```

마지막으로 하나. `down()` 은 `dropTable` 입니다. **데이터가 들어 있어도 묻지 않고 지웁니다.** 로컬에서는 편한 도구지만 운영 DB에서 `migrate:rollback` 을 치는 일은 없어야 합니다. 되돌려야 할 일이 생기면 되돌리는 마이그레이션을 새로 만들어 앞으로 나아가는 쪽이 안전합니다.

## 마무리

테이블 두 개를 만들었는데 화면은 2편의 환영 화면 그대로입니다.

그래도 이번 편에서 지나간 것들 — 인덱스 키 길이, `TINYINT(1)`, 콜레이션, `down()` 왕복 — 은 나중에 찾아오면 원인을 짚기 어려운 종류입니다. 만들 때 한 번 보고 넘어가면 다시 만날 일이 없습니다.

다음 회차에서는 `posts`, `comments`, `attachments` 셋을 만듭니다. 3편에서 설계한 인덱스 세 개를 실제로 걸고, 외래 키의 `CASCADE` 와 `SET NULL` 을 지정하고, 소프트 딜리트를 위한 `deleted_at` 을 답니다. 그러면 뼈대가 다 서고, 7편부터 화면이 나오기 시작합니다.
