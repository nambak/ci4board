`INSERT` 문을 쓰면 될 일처럼 보입니다. 그런데 그 길로 가면 만나는 사고가 하나 있어서, 그 이야기부터 하겠습니다.

## 1. 왜 시더인가 — 한글이 두 번 인코딩되는 사고

게시판 하나를 명령줄에서 넣어 보겠습니다.

```bash
mysql -h 127.0.0.1 -u root ci4board -e \
  "INSERT INTO boards (slug, name, created_at, updated_at) VALUES ('cli', '공지사항', NOW(), NOW());"
```

에러 없이 들어갑니다. 확인도 같은 방식으로 합니다.

```bash
mysql -h 127.0.0.1 -u root ci4board -e "SELECT slug, name FROM boards;"
```

```
slug    name
cli     공지사항
```

정상으로 보입니다. **여기서 확인을 끝내면 사고가 시작됩니다.**

같은 데이터를 문자셋을 지정한 클라이언트로 읽어 보겠습니다.

```bash
mysql --default-character-set=utf8mb4 -h 127.0.0.1 -u root ci4board -e \
  "SELECT slug, name, CHAR_LENGTH(name) AS chars, LENGTH(name) AS bytes, HEX(name) AS hex FROM boards\G"
```

```
 slug: ok
 name: 공지사항
chars: 4
bytes: 12
  hex: EAB3B5ECA780EC82ACED95AD

 slug: cli
 name: ê³µì§€ì‚¬í•­
chars: 12
bytes: 27
  hex: C3AAC2B3C2B5C3ACC2A7E282ACC3ACE2809AC2ACC3ADE280A2C2AD
```

`ok` 는 문자셋을 지정하고 넣은 행, `cli` 는 지정하지 않고 넣은 행입니다.

네 글자 12바이트여야 할 값이 **열두 글자 27바이트**가 됐습니다. 한글 한 글자의 UTF-8 세 바이트가 각각 별개의 문자로 취급되어 다시 UTF-8로 인코딩된 것입니다. 이걸 이중 인코딩이라고 합니다.

### 왜 명령줄에서는 멀쩡해 보였나

클라이언트가 서버에게 "내가 보내는 바이트는 latin1이다"라고 말했기 때문입니다.

```bash
mysql -h 127.0.0.1 -u root ci4board -e "SHOW VARIABLES LIKE 'character\_set\_%';"
```

```
character_set_client        latin1
character_set_connection    latin1
character_set_database      utf8mb4
character_set_results       latin1
character_set_server        utf8mb4
```

터미널은 UTF-8 바이트를 보내는데 클라이언트는 latin1이라고 신고했고, 서버는 그 말을 믿고 latin1 → utf8mb4 변환을 한 번 더 했습니다. 그리고 읽을 때도 같은 클라이언트가 utf8mb4 → latin1로 되돌려 보여주니 **넣은 사람 눈에는 정상으로 보입니다.**

더 고약한 건 반대쪽입니다. 같은 클라이언트로 보면 **제대로 들어간 행이 깨져 보입니다.**

```
slug    name
ok      ????        ← 올바른 데이터
cli     공지사항     ← 이중 인코딩된 데이터
```

사람은 여기서 판단을 뒤집기 쉽습니다. 멀쩡해 보이는 쪽을 맞다고 믿게 됩니다.

### 검색까지 서로 반대로 걸린다

인코딩 사고를 늦게 발견하게 되는 진짜 이유는 이것입니다.

```sql
SELECT slug FROM boards WHERE name LIKE '%공지%';
```

| 어느 클라이언트로 검색했나 | 결과 |
|---|---|
| latin1 (문자셋 미지정) | `cli` — 잘못 들어간 행이 걸린다 |
| utf8mb4 | `ok` — 올바른 행이 걸린다 |

검색이 되니까 데이터가 정상이라고 판단하게 됩니다. 문제는 몇 달 뒤 애플리케이션(당연히 utf8mb4로 접속합니다)에서 그 글이 검색되지 않을 때 드러나고, 그때는 이미 잘못된 데이터가 몇 만 건입니다.

원인을 `HEX()` 로만 잡을 수 있다는 것도 이 사고를 어렵게 만듭니다. 화면으로는 판별이 안 됩니다.

### 그래서 시더다

물론 명령줄에도 답은 있습니다. 매번 `--default-character-set=utf8mb4` 를 붙이면 됩니다. 문제는 **매번**입니다. 한 번 빠뜨리면 그 실행분만 조용히 오염됩니다.

CodeIgniter 시더는 이 문제가 없습니다. 2편에서 `.env` 에 적어 둔 두 줄을 쓰기 때문입니다.

```
database.default.charset  = utf8mb4
database.default.DBCollat = utf8mb4_unicode_ci
```

접속을 만들 때 이 값으로 문자셋을 정하므로, 어느 터미널에서 실행하든 결과가 같습니다. 게다가 데이터를 만드는 코드가 저장소에 남아 팀원끼리 공유됩니다. 명령줄 히스토리에만 있는 `INSERT` 문과는 다릅니다.

확인이 끝났으니 넣어 본 행은 지웁니다.

```sql
DELETE FROM boards;
```

## 2. `BoardSeeder` — 게시판 세 개

빈 파일부터 만듭니다.

```bash
php spark make:seeder BoardSeeder
```

```
File created: APPPATH/Database/Seeds/BoardSeeder.php
```

마이그레이션과 달리 파일 이름에 시각이 붙지 않습니다. 시더는 순서가 정해져 있지 않고 필요할 때 골라 부르는 것이기 때문입니다.

`app/Database/Seeds/BoardSeeder.php`

```php
<?php

namespace App\Database\Seeds;

use CodeIgniter\Database\Seeder;

class BoardSeeder extends Seeder
{
    public function run()
    {
        // FK 가 걸려 있어 TRUNCATE 는 거절당한다(ERROR 1701). DELETE 로 비운다.
        $this->db->table('boards')->emptyTable();

        $now = date('Y-m-d H:i:s');

        // 기본값과 다른 컬럼만 적는다. 나머지는 boards 의 DEFAULT 가 채운다.
        $boards = [
            [
                'slug'        => 'notice',
                'name'        => '공지사항',
                'description' => '운영 공지와 점검 안내입니다.',
                'per_page'    => 15,
                'categories'  => $this->json(['일반', '점검', '이벤트']),
                'use_comment' => 0,   // 공지에는 댓글을 받지 않는다
                'write_level' => 10,  // 관리자만 쓴다
                'sort_order'  => -10, // 목록 맨 앞
            ],
            [
                'slug'        => 'free',
                'name'        => '자유게시판',
                'description' => '무슨 이야기든 좋습니다.',
                'categories'  => $this->json(['잡담', '질문', '후기']),
                'use_secret'  => 1,
            ],
            [
                'slug'           => 'gallery',
                'name'           => '사진첩',
                'description'    => '찍은 사진을 올리는 곳입니다.',
                'skin'           => 'gallery',
                'per_page'       => 12,
                'categories'     => $this->json(['풍경', '일상', '장비']),
                'max_files'      => 10,
                'allowed_ext'    => 'jpg,jpeg,png,gif,webp',
                'download_level' => 0,
            ],
        ];

        foreach ($boards as $board) {
            $this->db->table('boards')->insert($board + [
                'created_at' => $now,
                'updated_at' => $now,
            ]);
        }
    }

    private function json(array $value): string
    {
        return json_encode($value, JSON_UNESCAPED_UNICODE);
    }
}
```

### 세 개를 고른 기준

하나만 만들면 이 강좌가 성립하지 않습니다. **게시판마다 다르다**는 걸 확인할 대상이 필요합니다.

| slug | 다른 점 | 어느 편에서 쓰나 |
|---|---|---|
| `notice` | 댓글 없음, 관리자만 쓰기, 목록 맨 앞 | 16편 권한, 27편 공지 고정 |
| `free` | 비밀글 허용, 기본값 대부분 유지 | 9~12편의 주 무대 |
| `gallery` | `gallery` 스킨, 이미지만 첨부, 한 페이지 12건 | 24편 첨부, 28편 스킨 분기 |

### 컬럼을 다 적지 않았다

각 배열의 키 개수가 다릅니다. `free` 는 다섯 개뿐입니다.

4편에서 `boards` 의 기본값 묶음이 곧 "새 게시판의 기본 정책"이라고 했습니다. 여기서 그 값을 씁니다. 적지 않은 컬럼은 DB가 채웁니다.

키가 제각각이라 `insertBatch` 는 쓸 수 없습니다 — 모든 행의 키가 같아야 하기 때문입니다. 세 건이라 한 건씩 넣어도 아무 문제가 없고, 무엇보다 **다른 점만 눈에 들어오는 코드**가 됩니다. 200건짜리 `PostSeeder` 는 반대로 갑니다(6절).

### `JSON_UNESCAPED_UNICODE` 를 왜 붙이나

`categories` 는 JSON 컬럼입니다. 그냥 `json_encode(['일반', '점검'])` 를 쓰면 이렇게 저장됩니다.

```json
["일반", "점검"]
```

동작에는 지장이 없습니다. `JSON_EXTRACT` 도 정상이고 애플리케이션에서 `json_decode` 하면 한글이 나옵니다. 그런데 DB에서 눈으로 읽을 수 없고, `LIKE '%일반%'` 같은 조회가 걸리지 않습니다.

플래그를 붙이면 원문 그대로 들어갑니다.

```
categories: ["일반", "점검", "이벤트"]
```

프레임워크도 같은 선택을 했습니다. 18편에서 쓸 Model의 `json-array` 캐스팅이 내부적으로 `JSON_UNESCAPED_UNICODE` 를 씁니다.

### `TRUNCATE` 가 아니라 `emptyTable()`

시더는 여러 번 돌리게 됩니다. 그때마다 `slug` 가 UNIQUE라 두 번째 실행은 `ERROR 1062` 로 죽습니다. 그래서 비우고 시작합니다.

비우는 방법으로 `TRUNCATE` 가 먼저 떠오르는데, 5편에서 건 외래 키 때문에 안 됩니다.

```sql
TRUNCATE TABLE boards;
```

```
ERROR 1701 (42000): Cannot truncate a table referenced in a foreign key constraint (`ci4board`.`posts`, CONSTRAINT `fk_posts_board`)
```

`posts` 도 마찬가지입니다 — `comments` 가 가리키고 있습니다. CodeIgniter의 `emptyTable()` 은 `DELETE FROM` 을 보내므로 이 제한에 걸리지 않습니다.

대신 `DELETE` 는 **auto_increment 를 되돌리지 않습니다.** 시더를 돌릴 때마다 id가 계속 커집니다. 이 글을 쓰면서 열댓 번 돌렸더니 이렇게 됐습니다.

```
id   slug
64   notice
65   free
66   gallery
```

게시판 세 개짜리 DB의 id가 64부터입니다. 동작에는 문제가 없지만, **id를 코드에 적어 두면 안 된다**는 뜻이기도 합니다. 5절에서 다시 나옵니다.

## 3. `UserSeeder` — Faker를 한국어로

```php
<?php

namespace App\Database\Seeds;

use CodeIgniter\Database\Seeder;
use Faker\Factory;

class UserSeeder extends Seeder
{
    /** 개발용 공통 비밀번호. 운영 데이터에는 절대 쓰지 않는다. */
    private const PASSWORD = 'ci4board!';

    /** 위 비밀번호를 password_hash() 로 한 번 계산해 박아 둔 값. */
    private const PASSWORD_HASH = '$2y$10$DgGwMXxwUU7yNWdny15fOeODeEHrhmmy2INTAtiKGCjUJQhY5uvN2';

    public function run()
    {
        $this->db->table('users')->emptyTable();

        $faker = Factory::create('ko_KR');
        $faker->seed(20260824);

        $now = date('Y-m-d H:i:s');

        $hash = self::PASSWORD_HASH;

        $rows = [
            ['email' => 'admin@example.com', 'username' => 'admin', 'nickname' => '관리자', 'level' => 10, 'role' => 'admin'],
            ['email' => 'manager@example.com', 'username' => 'manager', 'nickname' => '운영자', 'level' => 5, 'role' => 'manager'],
        ];

        for ($i = 1; $i <= 8; $i++) {
            $rows[] = [
                'email'    => "member{$i}@example.com",
                'username' => "member{$i}",
                'nickname' => $faker->name(),   // 겹쳐도 된다. nickname 은 UNIQUE 가 아니다
                'level'    => 1,
                'role'     => 'member',
            ];
        }

        foreach ($rows as &$row) {
            $row['password_hash'] = $hash;
            $row['created_at']    = $now;
            $row['updated_at']    = $now;
        }
        unset($row);

        $this->db->table('users')->insertBatch($rows);
    }
}
```

### Faker는 이미 들어와 있다

CodeIgniter의 `composer.json` 에 개발 의존성으로 들어 있습니다.

```json
"require-dev": {
    "fakerphp/faker": "^1.9",
    ...
}
```

`require-dev` 라는 게 중요합니다. 운영 서버에 `composer install --no-dev` 로 배포하면 **Faker는 없습니다.** 시더에서 부르는 건 괜찮지만(운영에서 시더를 돌릴 일이 없습니다), Model이나 Controller에서 부르면 로컬에서는 되고 운영에서만 죽습니다.

### `ko_KR` 을 직접 지정한다

CodeIgniter의 `Seeder` 에도 Faker를 꺼내는 방법이 있습니다.

```php
// system/Database/Seeder.php
public static function faker(): ?Generator
{
    if (! self::$faker instanceof Generator && class_exists(Factory::class)) {
        self::$faker = Factory::create();   // ← 로케일을 받지 않는다
    }

    return self::$faker;
}
```

로케일을 넘길 수가 없어서 영어 데이터가 나옵니다. 한글 목록을 보려고 시더를 만드는 마당이라, `Factory::create('ko_KR')` 로 직접 만듭니다.

```php
$faker = Factory::create('ko_KR');

echo $faker->name();     // 양정식
echo $faker->company();  // (주)종훈기획
echo $faker->city();     // 시흥시
```

### 해시를 계산하지 않고 박아 두는 이유

`password_hash()` 는 **일부러 느리게 만든 함수**입니다. 무차별 대입 공격의 속도를 떨어뜨리는 게 목적이라, 한 번 부르는 데 수십 밀리초가 걸립니다. 그래서 행마다 부르지 않고 한 번만 계산해 돌려 쓰는 것까지는 자연스럽습니다.

그런데 한 걸음 더 갔습니다. 계산 결과를 아예 상수로 박아 뒀습니다. 속도 때문이 아니라 **재현성 때문**입니다.

bcrypt 는 같은 비밀번호라도 매번 다른 소금(salt)을 뽑기 때문에 결과 해시가 실행할 때마다 달라집니다. 5절에서 시드를 고정해 200건을 똑같이 만들어 놓고도, 이 컬럼만은 계속 어긋나 있었습니다.

```
guest_password 2회 실행 차이: 42 줄
```

비회원 글 42건의 해시가 전부 다릅니다. 원래 비밀번호(`ci4board!`, `1234`)는 그대로이므로 로그인은 똑같이 되고, 달라지는 건 저장된 문자열뿐입니다. 그래도 "두 번 돌리면 같은 데이터"라고 말할 수 없게 되므로 미리 계산한 값을 넣었습니다.

**이건 시더에서만 허용되는 짓입니다.** 해시를 소스에 적어 두면 그 값이 저장소에 영원히 남고, `PASSWORD_DEFAULT` 가 나중에 더 강한 알고리즘으로 바뀌어도 따라가지 못합니다. 회원가입을 만드는 13편에서는 당연히 `password_hash()` 를 그때그때 부릅니다.

`nickname` 에 Faker가 만든 이름이 겹쳐도 그냥 둡니다. 4편에서 `nickname` 에 UNIQUE를 걸지 않기로 한 결정이 여기서 값을 합니다.

## 4. `PostSeeder` — 데이터에 굴곡을 준다

글 200건입니다. 전체 코드는 저장소에 있고, 여기서는 판단이 들어간 자리만 보겠습니다.

### 배분과 섞기

```php
private const COUNTS = ['notice' => 12, 'free' => 148, 'gallery' => 40];

$slots = [];

foreach (self::COUNTS as $slug => $count) {
    $slots = array_merge($slots, array_fill(0, $count, $slug));
}
shuffle($slots);
```

게시판별로 몰아서 넣으면 id가 뭉칩니다. `notice` 1~12번, `free` 13~160번… 이런 상태에서는 "전체 최신글" 같은 화면이 한 게시판만 보여줍니다(34편). 섞어야 id와 게시판이 흩어집니다.

### 작성 시각을 정렬해서 넣는다

```php
$dates = [];

for ($i = 0; $i < $total; $i++) {
    $dates[] = $faker->dateTimeBetween(self::SINCE, self::UNTIL);
}
usort($dates, static fn ($a, $b) => $a <=> $b);
```

이 세 줄이 없으면 나중에 헷갈립니다.

9편에서 만들 목록 쿼리는 `ORDER BY is_notice DESC, id DESC` 입니다. `created_at` 이 아니라 `id` 로 정렬합니다. 실제 서비스에서는 id 순서와 작성 순서가 같으니 문제가 없는데, **시더가 시각을 무작위로 넣으면 그 전제가 깨집니다.** 최신순 목록에 6개월 전 글이 맨 위에 오고, 정렬 코드를 의심하게 됩니다.

시각을 오름차순으로 정렬해 앞에서부터 쓰면 id 순서와 시간 순서가 일치합니다.

### 정상 데이터만 만들지 않는다

```php
private const NOTICES      = ['notice' => 3, 'free' => 2, 'gallery' => 0];
private const SOFT_DELETED = 5;
private const HIDDEN       = 3;
```

200건 전부가 평범한 공개 글이면, 9편에서 `deleted_at IS NULL` 을 빠뜨려도 화면이 똑같습니다. **필터가 일하는지 확인할 수 없는 데이터는 쓸모가 절반입니다.**

그래서 공지 5건, 소프트 딜리트 5건, 숨김 3건을 섞습니다. 목록에 보여야 하는 글은 200건이 아니라 192건이고, 이 숫자가 앞으로 몇 편 동안 확인용으로 쓰입니다.

비회원 글도 20% 정도 섞습니다. 7~12편이 비회원 기준으로 진행되기 때문입니다.

### 카운터는 0으로 둔다

```php
'comment_count' => 0,
'like_count'    => 0,
'file_count'    => 0,
```

`view_count` 는 무작위로 채우면서 나머지 셋은 0입니다.

3편에서 카운터를 **캐시**라고 정의했습니다. 원본은 `comments`, `post_likes`, `attachments` 에 있습니다. 지금 그 테이블들은 비어 있으므로, 캐시의 올바른 값도 0입니다. 목록이 그럴듯해 보이라고 `comment_count = 7` 을 넣으면, 22편에서 만들 재계산 명령이 첫 실행부터 200건을 "고치게" 됩니다. 데이터가 처음부터 거짓말을 하고 있으면 그 명령이 맞게 도는지 확인할 방법이 없습니다.

`view_count` 만 다른 이유도 3편에 있습니다. 셀 원본이 없어서 그 컬럼 자체가 원본입니다.

### 게시판 규칙과 어긋나지 않게

```php
// 공지사항은 write_level 이 10 이다. 비회원 글이 있으면 안 된다.
$isStaffOnly = $slug === 'notice';
$isGuest     = ! $isStaffOnly && mt_rand(1, 100) <= 20;

'user_id' => match (true) {
    $isGuest     => null,
    $isStaffOnly => $staffIds[array_rand($staffIds)],
    default      => $userIds[array_rand($userIds)],
},
```

시더는 애플리케이션을 거치지 않고 DB에 직접 씁니다. Validation도, 권한 검사도 지나갑니다.

처음 만든 시더는 `notice` 게시판에 비회원 글을 두 건 만들었습니다. `write_level = 10` 인 게시판이라 화면으로는 절대 만들 수 없는 글입니다. 16편에서 권한을 붙이고 나면 "존재할 수 없는 데이터"가 목록에 남아 있게 됩니다.

DB가 막아 주지 않는 규칙은 시더가 지켜야 합니다.

### id를 코드에 적지 않는다

```php
private function boards(): array
{
    $out = [];

    foreach ($this->db->table('boards')->get()->getResultArray() as $row) {
        $out[$row['slug']] = [
            'id'         => (int) $row['id'],
            'categories' => json_decode((string) $row['categories'], true) ?? [null],
        ];
    }

    return $out;
}
```

`'board_id' => 1` 로 적고 싶어지는 자리입니다. 2절에서 본 대로 `emptyTable()` 이 auto_increment를 되돌리지 않으므로, 두 번째 실행부터 게시판 id는 4, 5, 6이 되고 그다음엔 7, 8, 9가 됩니다. 하드코딩한 시더는 두 번째 실행에서 `ERROR 1452` 로 죽습니다.

바뀌지 않는 건 `slug` 입니다. 그걸로 찾습니다.

## 5. 시드를 고정했는데 결과가 달랐다

`PostSeeder` 에 이런 줄이 있습니다.

```php
$faker->seed(20260824);
```

Faker의 `seed()` 는 PHP의 난수 생성기를 통째로 고정합니다.

```php
// vendor/fakerphp/faker/src/Faker/Generator.php
public function seed($seed = null)
{
    if ($seed === null) {
        mt_srand();
    } else {
        mt_srand((int) $seed, self::mode());
    }
}
```

`mt_srand()` 를 부르므로 Faker뿐 아니라 `mt_rand()`, `shuffle()`, `array_rand()` 까지 함께 고정됩니다. 시더 안에서 이 셋을 마음 놓고 쓸 수 있는 이유입니다.

**같은 데이터가 나와야 하는 이유**는 이렇습니다. 목록 화면을 고치다 보면 어제와 다른 화면이 나옵니다. 그게 코드를 고쳐서인지 데이터가 달라져서인지 구분되지 않으면, 디버깅이 두 배로 어려워집니다.

그런데 두 번 돌려서 비교해 봤더니 달랐습니다.

```bash
php spark db:seed DatabaseSeeder && mysql ... > 1.txt
php spark db:seed DatabaseSeeder && mysql ... > 2.txt
diff 1.txt 2.txt | grep -c '^<'
```

```
185
```

200건 중 185건이 다릅니다. 제목도, 조회수도, 작성자도. 시드를 고정했는데도 그렇습니다.

의심 가는 곳이 둘이었습니다. 하나씩 떼어 재 봤습니다.

| 무엇을 고쳤나 | 200건 중 다른 행 |
|---|---|
| 아무것도 (처음 상태) | 185 |
| 날짜만 상수로 | 185 |
| 본문 생성만 반복문 밖으로 | 5 |
| 둘 다 | **0** |

(정확히는 셋이었습니다. 세 번째인 비밀번호 해시는 3절에서 이미 처리했습니다 — 난수열과 무관하게 bcrypt 소금이 매번 달라지는 문제라 성격이 다릅니다.)

### ① 반복문 안의 `realText()`

주범이었습니다.

```php
// 고치기 전
'content' => $faker->realText(mt_rand(150, 400)),
```

`realText()` 는 원본 텍스트를 마르코프 체인으로 이어 붙여 문장을 만듭니다. 코드를 보면 원하는 길이가 나올 때까지 다시 시도하는 구조입니다.

```php
// vendor/fakerphp/faker/src/Faker/Provider/Text.php
do {
    ++$iterations;
    // ...
    $result = $this->generateText($maxNbChars, $words);
} while (static::strlen($result) <= $minNbChars);
```

한 번 부를 때 난수를 몇 번 쓰는지가 만들어진 문장에 따라 달라진다는 뜻입니다. 이걸 다른 난수 호출들 사이에 끼워 200번 반복하니 결과가 흔들렸습니다.

본문 조각을 미리 만들어 두고 돌려 쓰는 쪽으로 바꿨습니다.

```php
$paragraphs = [];

for ($i = 0; $i < 24; $i++) {
    $paragraphs[] = $faker->realText(mt_rand(150, 400));
}

// 본문은 이 중에서 두셋을 골라 잇는다
private function content(array $pool): string
{
    $picked = [];

    for ($i = 0, $n = mt_rand(2, 3); $i < $n; $i++) {
        $picked[] = $pool[array_rand($pool)];
    }

    return implode("\n\n", $picked);
}
```

생성은 24번으로 끝나고, 반복문 안에는 `array_rand` 만 남습니다. 이것으로 185건이 5건까지 줄었습니다. 덤으로 빨라졌습니다 — 마르코프 생성 200번이 24번이 됐으니까요.

### ② 상대 날짜

남은 5건입니다. 작성 시각을 이렇게 뽑고 있었습니다.

```php
$faker->dateTimeBetween('-180 days', '-1 hour');
```

`-180 days` 는 **실행하는 순간**을 기준으로 계산됩니다. 1초 뒤에 실행하면 뽑을 수 있는 범위가 1초만큼 달라집니다.

범위가 달라지면 뽑히는 값만 달라지는 게 아닙니다. `mt_rand($min, $max)` 는 32비트 난수를 범위에 맞게 줄이는데, 그 과정에서 편향을 없애려고 **범위를 벗어난 값이 나오면 다시 뽑습니다.** 200번 뽑는 동안 그 재추첨이 한 번만 어긋나도 그 뒤의 난수열 전체가 밀립니다.

날짜를 상수로 박았습니다.

```php
private const SINCE = '2026-02-24 00:00:00';
private const UNTIL = '2026-08-23 23:59:59';
```

다시 재 봤습니다.

```
0
```

두 번 돌려도 200건이 완전히 같습니다.

대신 데이터가 낡습니다. 이 시더가 만드는 가장 최근 글은 언제 돌리든 2026년 8월 23일입니다. 재현성과 신선함 중 하나를 고르는 문제인데, 이 강좌는 재현성을 골랐습니다. 상수 두 개라 필요할 때 옮기면 됩니다.

> **Faker 한국어 본문의 정체.** `ko_KR` 로케일의 `realText()` 는 위키문헌에 있는 이광수의 소설 「유정」을 원본으로 씁니다(CC BY-SA 3.0). 그래서 생성된 본문이 "R는 약간 흥분된 어조를 늦추어서" 같은 소설 문장이 됩니다. 게시판 글처럼 읽히지는 않지만, 길이와 줄바꿈과 한글 인코딩을 시험하는 데는 충분합니다. 그럴듯한 게시판 본문이 필요하다면 직접 만든 문장 풀을 쓰는 편이 낫습니다.

## 6. `insertBatch` — 왕복을 줄인다

```php
foreach (array_chunk($rows, 100) as $chunk) {
    $this->db->table('posts')->insertBatch($chunk);
}
```

한 건씩 `insert()` 를 부르면 `INSERT` 문 200개가 나갑니다. `insertBatch` 는 `VALUES` 를 이어 붙여 한 문장으로 만들므로 100건씩 끊으면 두 번이면 끝납니다.

2,000건으로 재 봤습니다.

```
한 건씩 2000회 : 0.21초
100건씩 20회   : 0.04초
```

다섯 배쯤 차이납니다. 200건에서는 0.03초와 0.00초라 사실 아무래도 좋습니다. 그런데도 처음부터 배치로 쓰는 이유는, 데이터가 늘거나 DB가 다른 기계에 있을 때 이 차이가 그대로 커지기 때문입니다. 왕복 한 번의 값이 로컬에서는 거의 0이지만 네트워크 너머에서는 아닙니다.

100건씩 끊는 이유는 `max_allowed_packet` 입니다. 2,000건을 한 문장으로 만들면 쿼리 하나가 수 메가바이트가 되고, 서버 설정에 따라 거절당합니다.

### 인덱스는 그대로 일하는가

5편에서 500건으로 확인했던 목록 쿼리를 다시 던져 봅니다.

```sql
EXPLAIN SELECT id, title FROM posts
 WHERE board_id = (SELECT id FROM boards WHERE slug = 'free') AND deleted_at IS NULL
 ORDER BY is_notice DESC, id DESC LIMIT 20\G
```

```
          key: idx_board_list
      key_len: 10
          ref: const,const
         rows: 144
        Extra: Using where; Backward index scan
```

`idx_board_list` 를 그대로 씁니다. 그리고 `slug` 를 찾는 서브쿼리는 이렇게 나옵니다.

```
         table: boards
          type: const
           key: slug
         Extra: Using index
```

4편에서 `slug` 에 UNIQUE를 건 것이 여기서 일합니다. `type: const` 는 "한 건뿐임이 확실하다"는 뜻이고, 이 조회가 다음 편 라우팅의 첫 동작이 됩니다.

이번 편에서 오래 붙잡은 건 두 가지였습니다. 하나는 눈으로 보면 정상인데 실제로는 깨져 있는 한글이었고, 다른 하나는 시드를 고정했는데도 매번 달라지던 데이터였습니다. 둘 다 "일단 되는 것처럼 보이는" 상태를 지나쳤다면 훨씬 뒤에, 훨씬 비싼 값을 치르고 만났을 문제입니다. 시더가 단순히 데이터를 넣는 도구가 아니라 **확인 가능한 상태를 만드는 도구**인 이유가 여기 있습니다.

다음 회차부터 화면이 나옵니다. 7편에서 라우트를 **하나만** 만들고, 그 하나로 `/board/notice`, `/board/free`, `/board/gallery` 를 전부 받습니다. 게시판을 추가할 때 라우트를 추가하지 않는다는 것이 이 강좌가 말한 "설정만으로 게시판을 찍어낸다"의 첫 장면입니다.
